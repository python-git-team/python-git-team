# Contributing Guide

> 이 문서는 `python-git-team` 저장소에 기여할 때 지켜야 할 규칙을 정의한다.
> 이 프로젝트의 목적은 Python 기능 구현이 아니라 **Git 협업 과정을 경험하는 것**이다.
> 따라서 아래 규칙은 코드 품질보다 **Issue → Branch → Commit → PR → Review → Merge 흐름의 유지**를 우선한다.

---

## 0. 문서 구성

기록할 내용에 따라 문서를 나눈다. 다른 문서의 영역을 침범하지 않는다.

| 문서 | 기록하는 내용 | 소유 |
| :--- | :--- | :--- |
| `docs/CONTRIBUTING.md` | 평상시에 지켜야 할 협업 규칙과 절차 | B |
| `docs/conflict-resolution.md` | 실제로 발생한 충돌 사례와 해결 과정 | C |
| `docs/troubleshooting-log.md` | 명령 실습(amend / reset / revert / stash) 기록 | D (공동 편집) |
| `README.md` | 프로젝트 소개 | A |

이 문서는 **규칙**만 담는다. 개별 사례 기록은 위 표에 따라 해당 문서로 넘긴다.

## 1. Branch Strategy

### 브랜치 전략 선택: GitHub Flow

- 작업 기간이 짧고 배포 단계가 없어, `develop` 같은 중간 브랜치를 두면 관리 비용만 늘어난다.
- `main` 하나만 정상 동작 상태로 유지하면 되므로 규칙이 단순하고 4명이 동일하게 이해할 수 있다.
- 모든 변경이 Pull Request를 거치므로 리뷰와 이력 추적이 자연스럽게 강제된다.

> 이 저장소는 `main` + `feature/*` 구조만 사용한다. `develop` 브랜치는 만들지 않는다.

### main 브랜치

- 항상 정상적으로 동작하는 상태를 유지한다.
- 직접 push 하지 않는다.
- 모든 변경은 Pull Request를 통해 병합한다.
- `main`에는 다음 Branch Protection Rule을 적용한다.
  - Require a pull request before merging
  - Require approvals: 1명 이상

### feature 브랜치 naming rules

- 모든 기능 단위 작업은 `feature/*` 형식의 브랜치를 사용한다.

```text
feature/name-topic

(예시)
feature/minjun-string-utils
feature/seoyeon-math-utils
feature/jihoon-date-utils
feature/yujin-list-utils
```

- 영문 소문자와 하이픈(`-`)만 사용한다. 공백, 대문자, 한글은 사용하지 않는다.
- 브랜치는 반드시 최신 `main`에서 생성한다.

```bash
git switch main
git pull origin main
git switch -c feature/name-topic
```

- Merge가 끝난 브랜치는 원격과 로컬 모두에서 삭제한다.

```bash
git push origin --delete feature/name-topic
git branch -d feature/name-topic
```

## 2. 작업 단위 규칙

- 원칙은 **Issue 하나 = Branch 하나 = PR 하나**이다.
- 작업이 커지면 새로운 Issue로 분리한다.
- 아직 Merge하면 안 되는 작업은 별도 브랜치에서 유지하거나 Draft PR로 올린다.
- 한 PR에 서로 관련 없는 변경을 섞지 않는다. (예: 함수 추가 + 문서 수정)

---

## 3. Issue Rules (Issue 작성 규칙)

작업을 시작하기 전에 먼저 Issue를 생성한다.

Issue에는 다음 내용을 간단하게 작성한다.

- 작업 목적
- 작업 내용
- 완료 조건

```text
(예시)

# 문자열 유틸 함수 추가

## 목적
문자열 처리를 위한 기본 유틸 함수를 추가한다.

## 작업 내용
- 문자열 뒤집기 함수 구현
- 간단한 실행 예시 추가

## 완료 조건
- 함수가 정상적으로 동작한다.
- README 또는 docstring에 사용 방법이 설명되어 있다.
```

추가 규칙

- Issue 생성 후 본인을 Assignee로 지정한다.
- 다른 팀원의 담당 파일에 수정이 필요할 때도 **Issue로 요청**한다. 직접 수정하지 않는다.
- Issue는 연결된 PR이 Merge되면서 닫히도록 한다.

## 4. Commit Message Convention (Commit 메시지 규칙)

아래의 형식을 사용한다.

```text
type: subject
```

| type | 설명 |
| :--- | :--- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 또는 오류 수정 |
| `docs` | 문서 수정 |
| `refactor` | 기능 변경 없이 코드 구조 개선 |
| `test` | 테스트 추가 및 수정 |
| `chore` | 설정 및 기타 작업 |

세부 규칙

- subject는 영문 소문자로 시작하고 50자 이내로 작성한다. 끝에 마침표를 찍지 않는다.
- 명령형으로 작성한다. (`added average function` ❌ → `add average function` ⭕)
- 하나의 커밋은 하나의 의미 단위만 담는다.

```text
(예시)
feat: add average calculation
docs: add contributing guide
fix: handle empty list in calculate_average
```

## 5. Pull Request Rules (PR 작성 규칙)

| 키워드 | 내용 |
| :--- | :--- |
| `What` | 무엇을 변경했는지 작성한다. |
| `Why` | 왜 변경했는지 작성한다. |
| `How` | 어떻게 테스트했는지 작성한다. |
| `Issue` | 관련 issue를 다음과 같이 연결한다. <br> `Closes #이슈번호` |

> `Closes`와 번호 사이에 공백을 넣지 않는다. `Closes # 3`은 동작하지 않고 `Closes #3`만 Issue를 자동으로 닫는다.

```text
(예시)

## What
- calculate_average 함수를 추가했습니다.

## Why
- 숫자 리스트의 평균을 구하는 기본 유틸이 필요했습니다.

## How
- 파일을 직접 실행해 [1, 2, 3] → 2.0 을 확인했습니다.

Closes #3
```

추가 규칙

- PR 제목도 커밋 메시지와 동일하게 `type: subject` 형식을 따른다.
- 작업이 끝나지 않은 상태로 올릴 때는 **Draft Pull Request**로 생성한다.
- 리뷰어가 특히 봐줬으면 하는 부분이 있으면 PR 본문에 함께 적는다.

## 6. Code Review Rules (코드 리뷰 규칙)

- 본인 PR은 직접 승인하지 않는다.
- 최소 1명의 팀원이 리뷰한다.
- 단순히 `LGTM` 또는 `좋아요` 만 작성하지 않는다.
- 특정 코드나 파일을 근거로 질문, 개선 제안 또는 위험 요소를 작성한다.
- 작성자는 리뷰 의견에 답변하거나 실제 수정사항을 반영한다.

### 리뷰 담당

각자 **최소 2개**의 다른 팀원 PR을 리뷰한다. 담당은 아래와 같다.

| 리뷰어 | 리뷰 대상 |
| :--- | :--- |
| A | D, C |
| B | A, D |
| C | A, B |
| D | B, C |

### 리뷰 관점

무엇을 써야 할지 막힐 때는 아래 항목을 기준으로 본다.

| 관점 | 확인 내용 |
| :--- | :--- |
| 예외 입력 | 빈 값, `0`, 음수, `None`, 타입 불일치가 들어오면 어떻게 동작하는가 |
| 네이밍 | 함수·변수 이름만 보고 하는 일이 짐작되는가 |
| 중복 | 같은 로직이 다른 파일에 이미 있지 않은가 |
| 규칙 준수 | 브랜치명·커밋 메시지·PR 양식이 이 문서의 규칙을 지켰는가 |
| 문서 | 사용 예시나 docstring이 있는가 |

### 리뷰 기한

리뷰 기한은 **시간(24시간)이 아니라 팀 미션 일정(Day)을 기준**으로 한다.
Day 1에 올라온 PR을 Day 2 일정에 리뷰하면 등록 후 24시간을 넘길 수 있으므로, 두 기준이 충돌하지 않도록 아래와 같이 정한다.

| 구분 | 기한 |
| :--- | :--- |
| 미션 일정상 **Day 2 리뷰**로 배정된 PR | **Day 2 종료 시각(23:59)**까지 |
| 그 외 상시로 올라온 PR | 등록 후 **48시간** 이내 |
| 미션 **마감 당일**에 올라온 PR | 당일 안에 (마감 시각 전) |

- 미션 일정이 정해져 있는 PR은 **미션 일정이 우선**한다.
- 기한 안에 리뷰가 어려우면, 기한이 지나기 전에 PR에 코멘트로 미리 알린다.

### 리뷰 진행 절차

1. 리뷰어는 위 기한 안에 코멘트를 남긴다.
2. 작성자는 **최소 1개 이상의 리뷰 의견을 실제로 반영**하고 수정 커밋을 올린다.
3. 반영한 내용은 해당 리뷰 코멘트에 답글로 알린다.
4. 반영하지 않기로 한 의견도 이유를 답글로 남긴다.

> 지적은 사람이 아니라 코드를 대상으로 한다. "이거 고치세요"보다 "~하면 어떨까요?" 형태로 제안한다.

## 7. Merge Rules

### 병합 조건

Pull Request를 main에 병합하기 위해 다음 조건을 지킨다.

- 관련 Issue가 존재해야 한다.
- PR 본문에 What / Why / How 가 작성되어 있어야 한다.
- 다른 팀원의 코드 리뷰가 있어야 한다.
- 최소 1명의 승인을 받아야 한다.
- 필요한 리뷰 의견을 반영 후 병합한다.
- 충돌이 모두 해결되어 있어야 한다.

### 병합 담당 (누가 Merge 버튼을 누르는가)

- Approve가 달린 뒤 **Merge 버튼은 PR 작성자가 직접 누른다.** 리뷰어나 다른 팀원이 대신 병합하지 않는다.
  - 작성자가 변경 내용을 가장 잘 알고, 병합 직후 동작 확인과 브랜치 정리까지 이어서 책임질 수 있기 때문이다.
  - 승인만으로 자동 병합되지 않으므로, 작성자는 승인 이후 위 병합 조건을 다시 한 번 확인하고 병합한다.
- 작성자는 병합 전에 최신 `main`을 브랜치에 반영하고 충돌이 없는지 확인한다.

```bash
git switch feature/name-topic
git pull origin main
```

- 승인 후에도 작성자가 **48시간** 이상 병합하지 않고 그 PR이 다른 작업을 막고 있으면, PR에 코멘트로 알린 뒤 **승인한 리뷰어가 대신 병합**할 수 있다.
- 병합 방식이나 충돌 처리 방향을 작성자 혼자 판단하기 어려우면 병합하지 말고 PR 코멘트로 팀에 먼저 공유한다.

### 병합 이후

- 병합 방식은 **Merge commit**을 기본으로 한다. (이력을 그대로 남기기 위함)
- 작성자는 연결된 Issue가 닫혔는지, `main`이 정상 동작하는지 확인한다.
- 병합된 브랜치는 원격과 로컬 모두에서 삭제한다.
- 각자 로컬 `main`을 최신화한다. (`git switch main` → `git pull origin main`)

## 8. 충돌 발생 시 기본 대응 흐름

```text
충돌 발생
↓
충돌 내용을 팀원에게 공유
↓
충돌 원인 확인
↓
충돌 마커 확인 (<<<<<<< / ======= / >>>>>>>)
↓
두 변경 내용을 비교
↓
최종 코드 결정
↓
충돌 마커 제거
↓
테스트 실행
↓
충돌 해결 commit
↓
PR에 반영
↓
docs/conflict-resolution.md 에 기록
```

### 충돌 마커의 의미

```text
<<<<<<< HEAD
현재 내 브랜치의 내용
=======
병합하려는 쪽(main)의 내용
>>>>>>> main
```

- `<<<<<<<` ~ `=======` : 지금 내 브랜치가 가진 내용
- `=======` ~ `>>>>>>>` : 병합해 들어오는 쪽의 내용
- **임의로 한쪽을 지우지 않는다.** 상대 작성자와 상의한 뒤 남길 내용을 정한다.
- 해결 후 마커 세 줄(`<<<<<<<`, `=======`, `>>>>>>>`)을 모두 제거했는지 확인한다.

### 해결 명령

```bash
git switch feature/name-topic
git pull origin main   # CONFLICT 메시지 확인
git status             # 충돌 파일 목록 확인
# 파일 수정 후
git add 충돌파일
git commit
git push
```

### 충돌 예방

- 작업 시작 전에 항상 최신 `main`을 받아온다.
- 브랜치를 오래 유지하지 않는다. 작업이 끝나면 바로 PR을 올린다.
- 다른 팀원의 담당 파일은 직접 수정하지 않는다.

### 실습 목적의 의도적 충돌

이 프로젝트는 충돌 해결을 경험하기 위해 **의도적으로 충돌을 발생시킨다.** 이 경우에 한해 위의 예방 규칙과 파일 소유권 규칙의 예외를 인정한다.

- 실습용 충돌은 **사전에 해당 파일 소유자와 합의**하고, Issue로 선언한 뒤 진행한다.
- 담당 조합과 대상 파일은 아래와 같다.

| 충돌 | 대상 파일 | 담당 |
| :--- | :--- | :--- |
| #1 | `README.md` 의 같은 부분 | A · B |
| #2 | Python 파일 | C · D |

- 충돌은 **2회 이상** 발생시키며, 그중 **1회 이상은 비자명 충돌**로 만든다.
- 합의 없이 다른 팀원의 파일을 수정하는 것은 실습으로 인정하지 않는다.

### 자동으로 잡히지 않는 충돌 (비자명 충돌)

한쪽이 파일을 이동·삭제하고 다른 쪽이 그 파일의 내용을 수정한 경우, Git이 내용 충돌로 잡아주지 못하고 조용히 잘못 병합될 수 있다.

- 파일 이동·삭제·이름 변경은 **작업 전에 반드시 팀에 공유**한다.
- 병합 후에는 `git log --stat`과 실제 파일 실행으로 결과를 직접 확인한다.

## 9. 되돌리기 명령 사용 기준

커밋을 되돌리는 명령은 **이미 push 했는지 여부**에 따라 사용을 구분한다.

| 상황 | 사용 명령 | 설명 |
| :--- | :--- | :--- |
| push 전 로컬 커밋 | `git commit --amend` | 마지막 커밋의 메시지나 내용을 수정 |
| push 전 로컬 커밋 | `git reset --soft HEAD~1` | 커밋만 취소하고 변경 내용은 staged로 유지 |
| 이미 push 한 커밋 | `git revert <commit>` | 되돌리는 **새 커밋**을 추가해 이력을 보존 |
| 작업 중 브랜치 이동 | `git stash` / `git stash pop` | 작업 중인 변경을 잠시 보관 |

- **`main`과 공유 브랜치에 `push --force`를 사용하지 않는다.**
- 이미 push한 커밋에는 `amend`와 `reset`을 사용하지 않는다. 원격과 이력이 어긋나 다른 팀원의 작업이 유실될 수 있다.
- 되돌리기 명령을 실행했다면 상황 / 원인 / 절차 / 결과 / 주의점을 `docs/troubleshooting-log.md`의 본인 섹션에 기록한다.

## 11. 파일 소유권

파일별 소유자는 아래와 같다. (미션 역할 분담 기준)

| 담당 | 파일 |
| :--- | :--- |
| A | `src/string_utils.py`, `README.md` |
| B | `src/math_utils.py`, `docs/CONTRIBUTING.md` |
| C | `src/list_utils.py`, `docs/conflict-resolution.md` |
| D | `src/date_utils.py`, `docs/troubleshooting-log.md`, `SUBMISSION.md` |

- 자신의 담당 파일만 직접 수정한다.
- 다른 팀원 파일에 수정이 필요하면 **Issue 또는 PR Review로 전달**한다.
- 공통 파일(`README.md` 등)은 팀 합의 후 수정한다.
- 실습 목적으로 의도적인 충돌을 만들 때도 **사전에 해당 파일 소유자와 합의**한다. (8장)

### 예외: `docs/troubleshooting-log.md`

이 파일은 네 명의 실습 기록이 모두 모이므로 **공동 편집 파일**로 운영한다.

- D가 문서의 뼈대와 A / B / C / D 섹션을 만든다.
- 각 팀원은 **자기 섹션만** 직접 수정하고 커밋한다.
- 다른 팀원의 섹션은 수정하지 않는다.
- 불필요한 충돌을 줄이기 위해 기존 줄을 고치지 않고 자기 섹션 안에 내용을 추가하는 방식으로 작성한다.
